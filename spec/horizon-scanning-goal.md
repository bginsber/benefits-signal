# Goal: bring Benefits Signal to the Harvey Horizon Scanning horizon

**Status:** loop prompt · **Written:** September 1, 2026 · **Loop ledger:** `spec/horizon-progress.md`

This file is the prompt for an autonomous Ralph loop. Every iteration reads it in full, then does exactly one unit of work toward the next unmet milestone. It is written for Claude Fable 5.1 following Anthropic's prompting guide for that model. Do not edit this file during the loop unless a milestone's acceptance check is wrong; edit the ledger instead.

Launch from the repo root:

```
/ralph-loop "Read spec/horizon-scanning-goal.md in full and do the next iteration exactly as it instructs." --completion-promise "HORIZON GOAL MET" --max-iterations 40
```

---

## 1. The horizon

Harvey's Horizon Scanning (harvey.ai/blog/horizon-scanning-in-harvey) does five things. Benefits Signal already specifies an equivalent for four of them and deliberately declines the fifth.

| Harvey | Benefits Signal equivalent | State on 2026-09-01 |
|---|---|---|
| Describe a scan in plain language (topic, region, regulator); the system builds it | Five saved scans with plain-language charters (spec § 3) | Prose in the spec only. Not data. Nothing reads them. |
| 12,000+ sources across jurisdictions, plus public sources the user names | Seven curated interpretation sources plus a primary-authority layer (spec § 4, `spec/sources.yaml`) | Four RSS feeds and the Federal Register API are collected. Mercer, Segal, CourtListener, California DAS/CAC are configured but not collected. EBIA is email-only. |
| "What moved," most consequential first, with a relevance assessment per update | Now / Next / Watch tiers, confidence with rationale, fiduciary-duty tag (spec § 6.6) | Not implemented. The collated feed is chronological and unranked. The prototype's developments are hard-coded in `src/App.jsx`. |
| Email digests of daily changes | Daily collated RSS into Outlook (live); weekly assessed issue plus email digest (spec § 6.8) | Collated RSS is live on GitHub Pages. No assessed digest exists. |
| Alerts connect to downstream work in one system: memo revision, policy update, interactive timeline of upcoming obligations, shared scans | Closed list of internal next steps that require attorney review (spec § 8); obligations timeline and trustee-agenda filter (spec § 13, Phase 3) | Next-step buttons exist in the prototype and do nothing durable. No timeline. |
| Ask a question in plain language, grounded in the source | Deferred until the store is trustworthy (spec § 13) | Out of scope for this loop. |

The loop's job is to close the gap in the first five rows while keeping every constraint in § 2. When done, a paralegal can run one weekly command, receive a ranked candidate digest built from real documents against the five scans, review it, and release an issue that the existing front end renders from data.

## 2. Constraints that never move

These come from `AGENTS.md`, the spec (§ 1, § 11), and the firm. Treat a milestone that would break one as blocked, not as a reason to bend the constraint.

- **Public sources only.** No participant, employer, or client data enters the system. Never read a mailbox in this loop.
- **Nothing leaves the firm.** The pipeline never sends email, posts anywhere, or drafts external communications. Next steps create internal review items only, and every downstream action visibly requires attorney review.
- **The front end is the contract.** Every pipeline field populates something `src/App.jsx` already displays. No new screen. The scan view stays Now / Next / Watch with one status line, a short implication, and one disclosure. Metadata appears only inside an opened briefing. No dashboard chrome, no counts, no charts.
- **Never prompt toward a count.** An issue with zero developments is a legitimate output.
- **Attorney decisions stay with attorneys.** The items in spec § 14 have recommended defaults. Use the default, record it in the ledger under "Decisions taken by default," and move on. Do not implement the alternative too.
- **Keep the Sites handoff intact.** Do not modify `.openai/hosting.json`, `worker/index.js`, `scripts/prepare-sites-build.mjs`, or `tests/sites-worker.test.mjs`. `npm run build` and `npm run test:sites` must pass at the end of every iteration.
- **Zero-dependency scripts stay zero-dependency where they are today.** `scripts/collect.mjs` adds no packages. New pipeline scripts may add exactly two runtime dependencies: `@anthropic-ai/sdk` and one YAML parser. Nothing else without a ledger note explaining why.
- **Commit and push to `main` after every green iteration.** Ben has authorized the loop to push. A push touching `scripts/collect.mjs` or `.github/workflows/collate.yml` deploys the collector through `collate.yml`, so a pushed collector must have passed a live run in the same iteration. Never force-push and never rewrite history.
- **No Postgres yet.** Storage stays JSON files under `data/` until the Phase 1 exit criterion is met by humans, not by this loop.

## 3. Milestones

Work them in order. A milestone is done only when its acceptance check passes in the current iteration's own run, with the output pasted into the ledger. Reading the ledger is not evidence.

### M1 · Scans and sources become data
The five scan charters (spec § 3) and the scope rules (spec § 6.3) move into `spec/scans.yaml`, one entry per scan with `id`, `name`, `charter`, `primary_authorities`, `plan_types`, and `out_of_scope` rules. `scripts/collect.mjs` reads its source list from `spec/sources.yaml` instead of the hard-coded arrays, honoring `active` and `method`, and skipping methods it does not implement with a logged reason rather than an error. Adding a source or a scan must no longer require a code change.

Acceptance: `node --test tests/` includes a test that loads both files and asserts five scans, seven interpretation sources, and that every active source has a `method` the collector either implements or explicitly skips. `node scripts/collect.mjs --days 7` runs clean and `data/run-log.json` lists every active source with `ok`, `items`, or a `skipped` reason.

### M2 · Close the source gaps the spec already verified
Add collectors for the sources `spec/sources.yaml` marks reachable but not yet collected: CourtListener v4 opinion search for the Ninth Circuit (token from `COURTLISTENER_TOKEN` if present, anonymous otherwise), California DAS / DIR / CAC bulletin and meeting pages (plain HTML), Mercer's Law & Policy index page, and Segal's underlying JSON endpoint if it can be found without a browser. Each new collector stores the same document shape `storeItems` already writes, plus native structured fields (docket number, `date_filed`) where the source has them. Add the "source silent for N days" notice: the collector fetches the previous `run-log.json` from the Pages URL when `FEED_URL` is set, carries a `consecutive_failures` count per source, and emits a GitHub warning annotation at three or more.

Do not work around bot protection. If a source blocks the fetch (Wagner's Cloudflare challenge, dol.gov, hhs.gov), record it as a partial failure with retry-and-backoff only, and note it in the ledger. EBIA stays uncollected; it needs the firm mailbox and is out of this loop's reach.

Acceptance: a test per new collector runs its parser against a saved fixture under `tests/fixtures/` and asserts item count, link, date, and structured fields. A live `node scripts/collect.mjs --days 30` shows each new source with `ok: true` or a named, non-code failure.

### M3 · Normalize and scan-match with the model
`scripts/triage.mjs` reads `data/collected/`, produces a two-sentence neutral summary per document (never shown to readers), and for each document returns one `ScanMatch` row per scan: `score`, `in_scope`, `reason`. Out-of-scope documents are written to `data/omitted/` with the model's reason verbatim; nothing is deleted. Prompts live under `prompts/` as versioned files with a `version:` header, and every output records the prompt version that produced it. Model calls go through `@anthropic-ai/sdk`; see § 5 for the API facts to use.

Fixture mode is mandatory: `--fixture` replays recorded responses from `tests/fixtures/model/` so the test suite passes with no credentials. Before making a live call, run `ant auth status`; only if it reports no credential and `ANTHROPIC_API_KEY` is unset do you record "no credentials" in the ledger and continue in fixture mode.

Acceptance: `node --test tests/` covers the match output schema and the omission path in fixture mode. One live run over the current `data/collected/` writes `data/matches/` and `data/omitted/`, and the ledger records how many documents landed in each scan and how many were omitted.

### M4 · Cluster, verify, assess into `Development` candidates
`scripts/assess.mjs` groups in-scope documents from the current window plus the trailing thirty days by underlying legal development (same rule, same case, same deadline, not merely the same topic), attaching to an existing open development when one exists. For each cluster it locates primary authority (Federal Register document number, regulations.gov docket, CourtListener docket or opinion, IRS guidance number) and records a `VerificationRecord` per field. It then produces a candidate that validates against `spec/issue-schema.json`, with these rules enforced in code as well as in the prompt: an unconfirmed deadline cannot place an item in NEXT or NOW; confidence follows verification, not fluency; the supporting passage is a verbatim quotation of at most one short paragraph, with its document reference; the next step comes from the closed list in spec § 8; the fiduciary-duty tags come from the taxonomy in spec § 7 with a one-line justification each, and "None — settlor or administrative" is a valid answer.

Acceptance: `node --test tests/` validates fixture candidates against `spec/issue-schema.json` and unit-tests the tier rule and the confidence rule with cases that must fail. One live run writes `data/candidates/` and the ledger lists each candidate's headline, tier, confidence, and verification result.

### M5 · Weekly candidate digest for the paralegal
`scripts/digest.mjs` renders the candidates as the paralegal will see them: each candidate exactly as it would render in the newsletter, followed by the assessment's justifications, the verification record, and the cluster members. Output is a Markdown file under `data/digests/` and an RSS item appended to a second feed, `_site/review.xml`, so the digest reaches Outlook the same way the collated feed does. Review decisions are recorded by hand in `data/reviews/<issue>.json` in the `ReviewDecision` shape (spec § 5); the publisher in M6 reads that file. Add `.github/workflows/triage.yml` on a weekly Wednesday cron that runs collect, triage, assess, and digest, but leave it disabled with a comment until Ben enables it.

Acceptance: `node scripts/digest.mjs --fixture` produces a Markdown digest and a valid `review.xml` from fixture candidates, and a test asserts both. The ledger records the digest path and a sample review file.

### M6 · The front end reads data
Move the illustrative August 26 issue out of `src/App.jsx` into `public/issue.json` in the exact `spec/issue-schema.json` shape, and have `App.jsx` fetch it at load. `scripts/publish.mjs` reads approved candidates and the review file and writes `issue.json` plus the source log from real `SourceLogEntry` records (verified, kept, merged, omitted). A zero-development issue renders the masthead with "Nothing requires your attention this week" and an empty page below it. A development carried forward from a previous issue shows that in the expanded view rather than as new. No visual change to any existing screen.

Acceptance: `npm run build`, `npm run test:sites`, and `node --test tests/` pass. `dist/client/` still contains the built app. A test renders the publisher's output for an empty issue and for a carried-forward issue and asserts the two strings above.

### M7 · Upcoming obligations and the trustee-agenda filter
Two Phase 3 items that map to Harvey's "interactive timeline of upcoming obligations" and "shared scans," done within the quiet design. `scripts/publish.mjs` adds an `obligations` array to `issue.json`: every confirmed deadline and effective date across open developments, plus Federal Register comment deadlines that matched a scan, sorted by date. The front end shows it as one additional disclosure at the foot of the issue, a dated list in the reading column, nothing more. The digest gains a `--trustee-agenda` flag that filters to developments carrying at least one fiduciary-duty tag other than "None," as a handout the attorneys may choose to use.

Acceptance: fixture-driven tests for both outputs. `npm run build` and `npm run test:sites` pass. A screenshot of the obligations disclosure open and closed is saved under `design-qa/` and the ledger confirms it introduces no chrome outside the reading column.

### Out of scope for this loop
Natural-language questions against the store. Any external email. Any drafting of client alerts or trustee communications. Reading EBIA from a mailbox. Postgres. New screens. Changing the seven sources. Anything in spec § 14 beyond applying its recommended default.

## 4. How each iteration runs

You are operating autonomously. The user is not watching in real time and cannot answer questions mid-task, so asking "Want me to…?" or "Shall I…?" will block the work. For reversible actions that follow from this document, proceed without asking. Stop only for destructive actions or genuine scope changes the user must decide. Offering follow-ups after the task is done is fine; asking permission before doing the work is not.

1. **Orient.** Read `spec/horizon-progress.md` and `git log --oneline -20`. Then run the acceptance check of the first milestone the ledger marks incomplete. If it already passes, mark it done with the output and move to the next. Reading the ledger is not evidence; the run is.
2. **Announce.** In one line, say which milestone and which slice of it this iteration will finish.
3. **Gather.** First privately list what you need next; then request every file and command result that doesn't depend on another's result in this one response.
4. **Build.** Prefer surgical edits over whole-file rewrites; the number of tokens used to edit files is best minimized when it will not change the result. Tests go in `tests/` as `node --test` files sized like `tests/sites-worker.test.mjs`, roughly one focused test per stated behavior. Scratch scripts and quick checks need not be kept; do not turn them into permanent test files.
5. **Keep to the milestone.** If you find a pre-existing bug, a performance concern, or behavior this document doesn't mention, don't fix, optimize, or extend it unless the milestone cannot work without it; record it under "Follow-ups" in the ledger. Where a milestone is ambiguous, implement the reading its wording and the surrounding code most directly support, state that assumption in the ledger, and don't build for the other readings as well.
6. **Verify.** Run `npm run build && npm run test:sites && node --test tests/` and the milestone's acceptance check. Paste the actual output into the ledger. If anything fails, that is the iteration's remaining work, not a note.
7. **Commit and push.** One commit per coherent step, message in the imperative, ending with the two trailer lines already used in this repo's history (`Co-Authored-By` and `Claude-Session`). Push to `origin main` only after step 6 is green. If the push is rejected, fetch and rebase onto `origin/main`, re-run step 6, and push again; never force.
8. **Record.** Append an entry to the ledger (format in § 6). Then check your last paragraph. If it is a plan, a question, a list of next steps, or a promise about work you have not done, do that work now with tool calls. End the iteration only when the slice is complete or blocked on something only Ben can provide.
9. **Finish.** Output `<promise>HORIZON GOAL MET</promise>` only when every acceptance check in § 3 passed in this iteration's own run and the ledger shows the output. Never output it otherwise.

Before running a command that changes system state, check that the evidence actually supports that specific action. A source returning 403 today may pass tomorrow; that is a ledger note, not a reason to rewrite the fetcher.

## 5. API facts for the pipeline scripts

These override anything remembered from training. Use `@anthropic-ai/sdk` in ESM JavaScript, `new Anthropic()` with no arguments so credentials resolve from `ANTHROPIC_API_KEY` or an `ant auth login` profile.

- **Model.** Default every stage to `claude-opus-5`. Set depth with `output_config: { effort: "low" }` for normalize and scan match and `"high"` for verify and assess. Do not add a second, cheaper model until a ledger entry shows measured cost or quality that justifies it; one model means one cache namespace.
- **Thinking.** Omit the `thinking` parameter or pass `{ type: "adaptive" }`. Never send `budget_tokens`.
- **Structured output.** Use `output_config: { format: { type: "json_schema", schema } }` on `client.messages.create`, with a schema derived from `spec/issue-schema.json` for assess and small purpose-built schemas for match and cluster. Never use assistant prefill and never use forced `tool_choice`; both return errors on current models.
- **Caching.** Put the scan charters, the fiduciary-duty taxonomy, and the closed next-step list in `system` with `cache_control: { type: "ephemeral" }` on the last stable block, and keep per-document content in `messages`. Confirm `usage.cache_read_input_tokens` is non-zero on the second call of a run and record it in the ledger.
- **Refusals.** Check `stop_reason` before reading `content`; a `"refusal"` on a regulatory document is a defect to record, not to retry.
- **Cost.** Log `usage` per call to `data/run-log.json` so the weekly spend is visible.

## 6. Rules for the pipeline's own prompts

The prompting guide applies to the prompts under `prompts/` as much as to this document.

- **Quote, don't reproduce.** The assess prompt includes one complete example of a correct response: the cluster, the response, and a sentence explaining why it is correct. The example shows the supporting passage as a marked quotation with its document reference and every other sentence in the model's own words.
- **Verify before asserting.** The verify prompt states that recognizing a rule or a case is not the same as knowing its current status, and that status and dates come from the primary document supplied in the request, never from memory. When no primary document is supplied, the model records `unconfirmed` rather than answering.
- **Never toward a count.** No prompt mentions how many developments an issue should have or implies that finding something is better than finding nothing.
- **Lower when unsure.** Between two tiers, choose the lower and explain; between two confidence levels, choose the lower.
- **Say what you mean.** Prompts and the text the model writes for trustees use direct statement over metaphor. When a literal phrase is available, use it.

## 7. Ledger format

`spec/horizon-progress.md` is the loop's memory across iterations. Each entry preserves, exactly: (1) difficulties that came up and how they were handled; (2) approaches tried or set aside, and why; (3) anything decided, ruled out, or established as a constraint, stated exactly; (4) where things stand, per milestone; (5) anything open or expected next; (6) specifics that would be hard to reconstruct, such as URLs, endpoint shapes, counts, and exact command output. Be complete on these even at the cost of length; keep everything else short.

```
## Iteration N · YYYY-MM-DD · Milestone Mx
Slice: one line.
Done: what changed, with file paths.
Evidence: fenced command output from this iteration.
Decisions taken by default: spec § 14 items applied, or "none".
Assumptions: readings chosen where the milestone was ambiguous.
Follow-ups: pre-existing issues noticed and left alone.
Blocked: what only Ben can provide, or "nothing".
```
